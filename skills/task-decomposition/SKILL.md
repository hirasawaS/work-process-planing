# Skill: タスク分解

## 目的

大きな仕事を、実行可能な子タスクに分解する。

目標は、見た目の細かさではなく、実行可能でレビュー可能な粒度に落とすことだ。

## 原則

タスクが実行可能とは、次の一手が明確であることだ。

「このタスク、具体的にどう着手する？」に答えられないなら、
そのタスクはまだ粗い。

## 各子タスクに最低限必要な定義

各タスクには、次を定義する。

- Input
- Action
- Output
- Done
- Dependency
- Blocker

日本語にすると、次の意味になる。

- 入力
- 実行すること
- 成果物
- 完了条件
- 依存関係
- ブロッカー

## ガイド

### Input

このタスクを始める前に、何が必要か。

### Action

何を具体的に行うのか。

### Output

何が生成されるのか。
発見、判断、ドラフト、資料など。

### Done

何をもって完了とするのか。

### Dependency

このタスクの前提となるものは何か。

### Blocker

何が進行を止める可能性があるのか。
不足している情報や権限や前工程の依存関係は何か。

## ルール

Missing Information は仮定に変えない。

もしタスクが必要な事実に依存しているなら、
それを推測で埋めずに、情報収集タスクとして切り出す。

## 実行前の確認項目

タスクが妥当かどうかは、次を見て判断する。

- 入力が明確か
- 実行内容が明確か
- 成果物が明確か
- 完了条件が明確か
- 依存関係とブロッカーが見えているか
- レビューできる粒度か

どれか一つでも曖昧なら、タスクはまだ粗い。

## アンチパターン

大きな目的を「調査する」「確認する」「整理する」などの作業名で放り込まない。

それでは、何をもって完了とするのかが決まらない。

「Input / Action / Output / Done」がないタスクは、
まだ曖昧な意図に過ぎない。

## レビュー質問

「この子タスクは、仮定なしで実行可能か？」

答えられないなら、それはまだ粗い。

## 実務上の習慣

分解するときは、次の形を使う。

- Input → Action → Output → Done

これで、曖昧な作業を、レビュー可能な実行単位に変える。

大事なのは、たくさんのタスクを作ることではない。
曖昧な作業を、確認可能で修正可能な単位に変えることだ。
