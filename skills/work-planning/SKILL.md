# Skill: ワークプラン

## 目的

Work Plan は、やることリストではない。
Work Plan は、仕事を成立させるための設計である。

この Skill は、仕事の定義を、実行可能な計画へ落とし込むためのものだ。

## 核となる区別

### タスクリスト

タスクリストは、順番にやることを並べたものだ。

### Work Plan

Work Plan は、仕事が成立するかどうかと、そのために必要な条件を設計するものだ。

大事な違いは次の通り。

- タスクリストの問い: 「次に何をやるか」
- ワークプランの問い: 「この仕事が成立するには何が必要か」

## 含めるべき要素

Work Plan には、次を含める。

- Work Definition
- Sub-goals
- Required Outputs
- Required Inputs
- Dependencies
- Risks
- Execution Sequence
- Plan Review

日本語でいうと次のような要素だ。

- 仕事の定義
- サブゴール
- 必要な成果物
- 必要な入力
- 依存関係
- リスク
- 実行順序
- 計画レビュー

## 重要な原則

### 1. 仕事の定義を先に決める

計画は、目的・成果・制約・完了条件が明確な状態から始まるべきだ。

### 2. サブゴールで構造を作る

大きな仕事を、意味のある部分に分ける。

### 3. 成果物で計画を具体化する

各段階で何を出すのかを明確にする。
成果物がない計画は曖昧で、レビューしづらい。

### 4. 必要な入力で不足情報を見える化する

何の情報や判断が必要なのかを明示する。

### 5. 依存関係とリスクを計画に入れる

順番やボトルネック、不確実性を無視した計画は、実行時に壊れやすい。

### 6. 実行順序と仕事成立条件は別物

順番が整っていても、仕事が成立する前提がなければ意味がない。

### 7. Knockout 条件を早めに確認する

実行開始前に、次のような条件を疑う。

- 必要なデータがない
- 権限がない
- 前工程が終わっていない
- 納期と工数が見合わない
- 成果物の定義が曖昧

これらがあると、途中で破綻する。

## レビューの視点

AI に次の問いでレビューさせる。

「この Work Plan で仕事は成立するか？」

このレビューでは、単に手順が並んでいるかどうかではなく、
仕事が本当に成立しうるかを見ている。

確認すべき観点は次の通り。

- 目的は明確か
- 成果物は具体的か
- 必要な入力は見えているか
- 依存関係は認識されているか
- リスクはどこにあるか
- 実行順序は妥当か
- 不足情報は明示されているか
- 最も壊れやすい前提は何か

## 計画レビューの質問例

- 目的はまだ明確か
- 今回はタスクを並べているだけか、仕事成立条件を設計しているか
- 隠れた前提はあるか
- まだ不足している情報は何か
- 最初のレビュー地点はどこか
- どこでこの計画は破綻するか
- どこが最も脆いか

## ルール

やることを並べただけで「計画済み」とは言わない。

計画が妥当なのは、現状の制約と不確実性の中で、
その仕事が成立しうると説明できるときだ。

## 実務上のアンチパターン

粗い実行順序と妥当な Work Plan は違う。

手順が並んでいても、必要な入力が不足している、
前提が曖昧、依存関係が見えていない場合がある。

計画の目的は、一覧を作ることではない。
仕事が構造的に成立するかを見える化することだ。
