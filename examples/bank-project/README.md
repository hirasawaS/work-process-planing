# Example: 銀行案件の事例

この事例は意図的に一般化したものです。
銀行固有の手順書や顧客情報ではありません。
仕事計画でよく起きる失敗パターンを、汎用的な形で示すための事例です。

## もともとのパターン

過去の案件では、次のようなざっくりした計画が使われていました。

```text
過去案件の機能一覧
→ 不要な機能を削る
→ 必要な機能を足す
→ 現行案件の機能一覧
→ 機能一覧から課題を整理する
```

見た目は効率的に見えましたが、粒度が粗すぎました。

実際には、以下のような事実ベースの流れが必要でした。

```text
現行の仕様書・設計書を確認する
→ AS-IS の事実を理解する
→ 過去案件との差分を洗い出す
→ 対象を In Scope / Out of Scope / 要確認 に分類する
→ 課題を議論用の構造化ポイントに変える
→ 機能一覧を作る
→ 早めにレビューと反証を行う
```

## 何が問題だったか

実際の作業では、判断する前に AS-IS の事実確認が十分でありませんでした。
依存していたのは次のようなものです。

- 営業資料
- 既存ドキュメント
- 過去案件の記憶
- 個人の解釈

つまり、必要な情報が不足しているのに、根拠ではなく仮定で埋めていたのです。

その結果、次のような問題が起きました。

- どの判断がどの根拠に基づいているのか不明瞭
- 次に何をすべきかわからない
- 必要な入力が遅れて見つかる
- 手戻りと反復が増える

## 一般化した教訓

問題は単に Work Plan が下手だったわけではありません。

より深い問題は次のことです。

「子タスクが、実行可能な粒度まで分解されていなかった」

これはよくあるパターンです。

- 全体の計画はそれらしく見える
- 次の階層のタスクがまだ粗い
- 仕事が、明確に特定されていない不足情報に依存している
- 必要な事実が確認される前に実行が始まる

## 一般原則

大きな仕事が曖昧なとき、解決策は抽象化した計画言語を増やすことではありません。
必要なのは、仕事を実行可能な詳細まで落とすことです。

各子タスクは次を定義する必要があります。

```text
Input
→ Action
→ Output
→ Done
```

これにより、次のことが明確になります。

- 何の情報が必要か
- 何を実際にするのか
- どんな結果が出るべきか
- 何をもって完了とするのか

ここが曖昧なままだと、そのタスクは概念的な作業に留まります。

## なぜ重要か

タスクが実行可能なのは、次を答えられるときです。

- 始める前に何が必要か
- 何をするか
- 何を成果物として出すか
- どうやって完了を判定するか

計画にも同じことが言えます。

- 入力が曖昧なら仮定に頼らない
- 行動が曖昧ならタスクを細かくする
- 成果物が曖昧なら実行に十分な粒度ではない

## Missing Information のルール

Missing Information は仮定に変えてはいけない。

つまり次のように扱うべきです。

- 根拠が不足していれば事実確認タスクを作る
- 判断が止まっていれば、判断責任者と不足情報を明示する
- 依存関係が不明なら、前に解消してから進む

## 適応のためのフィードバックループ

この事例では、次の短いループが有効でした。

```text
Plan
→ Rough Output
→ Review
→ Assumption Update
→ Plan Update
```

これは、現実の仕事が最初の計画通りに進むことは稀だからです。
ラフなアウトプットは、早くギャップや誤った仮定、欠けている証拠を見つけられる利点があります。

目的は変化を避けることではない。
変化を早く見つけて、仕事の目的を損なわずに計画を更新することです。

## まとめ

本当の教訓はシンプルです。

仕事計画が失敗するのは、目標が大きすぎるからではなく、子タスクが実行可能な粒度になっていないからです。

実行可能性は次を定義することで生まれます。

- 必要な入力
- 実際の行動
- 期待される成果物
- 完了条件

この条件が揃って初めて、仕事は設計可能で、レビュー可能で、適応可能になります。
